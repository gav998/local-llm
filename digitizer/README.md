# Digitizer

Digitizer размечает PDF прямоугольниками, распознаёт каждый прямоугольник через
локальный PaddleOCR и хранит весь результат в одном Markdown-файле рядом с PDF:

```text
document.pdf
document.pdf.digitizer.md
```

Исходный PDF не изменяется. JSON/JSONL-файлов документа, внутренних ID,
шаблонов, групп, материализованного результата и миграций старой схемы нет.

## Модель данных

Markdown является единственным источником данных. Один объект начинается с
маркера типа, каждая область — со следующего маркера, а её текст идёт сразу за
ним:

```md
<!-- digitizer:object {"type":"document_header"} -->
<!-- digitizer:region {"field":"organization","page":1,"rect":[0.12,0.08,0.44,0.06],"rotation":0,"status":"recognized"} -->
ООО «Пример»
<!-- digitizer:region {"field":"approval","page":1,"rect":[0.58,0.07,0.31,0.15],"rotation":0,"status":"recognized"} -->
Генеральный директор Иванов И. И.

<!-- digitizer:object {"type":"table"} -->
<!-- digitizer:table {"field":"body","page":3,"rect":[0.06,0.22,0.88,0.61],"rotation":0,"status":"recognized","grid":{"x":[0,0.5,1],"y":[0,0.5,1],"statuses":[["recognized","recognized"],["recognized","recognized"]]}} -->
| 1 | 2 |
| --- | --- |
| Изделие А | 12 |
| Изделие Б | 7 |
```

Порядок объектов и областей в файле является их порядком в приложении. Ссылок и
ID нет. Несколько блоков строк одной таблицы — это несколько `digitizer:table`
маркеров внутри одного объекта, в том числе на разных страницах.

`rect` содержит нормализованные координаты `[x, y, width, height]`. Для таблицы
`grid.x` и `grid.y` — строго возрастающие границы от `0` до `1`, а
`grid.statuses` хранит статус каждой независимо распознаваемой ячейки.

Поддерживаются статусы `pending`, `queued`, `running`, `recognized`, `modified`
и `error`. После нового запуска временные `queued`/`running` читаются как
`pending`. Текст ошибки присутствует только у области со статусом `error`.

## Типы и OCR

Предметная схема целиком находится в `config.yaml`. Корневой ключ только один —
`types`; первый тип используется первым в интерфейсе. У типа есть отображаемое
имя и словарь полей. Поле с `kind: grid` является таблицей, остальные поля —
обычными текстовыми областями. Каждому полю обязателен собственный `prompt`.

Тип объекта и тип поля не влияют на OCR. Поток всегда одинаков:

```text
PDF → прямоугольник → PNG-фрагмент → PaddleOCR → Markdown
```

Табличный блок делится линиями сетки. Каждая ячейка отправляется в тот же OCR
отдельно, а переносы строк результата ячейки заменяются пробелами. Несколько
блоков строк можно добавить в один объект таблицы.

Кнопка `✦ ИИ` отправляет только один текстовый блок в OpenAI-совместимый API с
промптом его поля. У таблицы такая кнопка находится в каждой ячейке: таблица
целиком в LLM никогда не отправляется. Ответ модели принимается без проверки
структуры и подставляется как новый текст блока. Для Markdown-таблицы технически
неизбежное экранирование `|` и переводов строк выполняется при сборке строки.

## Интерфейс

Слева показан PDF. Проведите мышью по странице, затем выберите новый или
существующий объект и тип поля. OCR запускается сразу. Рамки можно переносить,
растягивать за нижний правый маркер и поворачивать на 90°. После изменения
геометрии рамка получает статус `modified`; повторный OCR запускается вручную.

Разделители таблицы перетаскиваются прямо на PDF. Число строк и столбцов также
меняется кнопками в карточке блока. Справа находятся объекты и редактируемый
Markdown. Кнопка «Применить» перечитывает ручные изменения Markdown, а
«Сохранить» атомарно записывает sidecar рядом с PDF.

## Запуск

На целевой Windows 11 запустите `start.bat`. Portable Python и зависимости
остаются внутри каталога Digitizer; системный профиль и `PATH` не изменяются.
PaddleOCR и llama.cpp могут запускаться отдельно. По умолчанию используются:

```text
PaddleOCR: http://127.0.0.1:9399
OpenAI API: http://127.0.0.1:6381/v1
Digitizer:  http://127.0.0.1:9400
```

Старые `.digitizer.json` не читаются и автоматически не мигрируются.
